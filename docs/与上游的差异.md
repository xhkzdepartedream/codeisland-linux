# 与上游的差异

上游是 [wxtsky/CodeIsland](https://github.com/wxtsky/CodeIsland)（MIT，2495★，2026-10 仍在提交），macOS，Swift。

## 一句话

**复用**线协议、事件名映射表、hook 语义、安全契约。**重写**桌面层、进程模型、hook 配置写入器。

上游仓库里已经有一份 Windows 移植（`windows/` 目录，作者 feelingsa，PR #275，2026-08-15，C#/.NET 8 + WPF），它的移植原则原话是「复用协议、事件模型、Hook 语义、资源和交互流程，重写 macOS 专属桌面层」。Linux 版沿用同一条原则。

## 上游结构与本项目的对应

| 上游 | 规模 | 本项目 | 处置 |
|---|---|---|---|
| `Sources/CodeIsland/` | 97 个 Swift 文件 | `shell/`（阶段 1 起） | **重写**，全是 SwiftUI/AppKit，画在物理刘海里 |
| `Sources/CodeIslandCore/` | 50 个文件 | `crates/codeisland-core/` | **部分移植**，见下 |
| `Sources/CodeIslandBridge/main.swift` | 735 行 / 30 KB | `crates/codeisland-bridge/` | **按行为重写**，不逐行翻译 |
| `android-watch/`、`ios/`、`apple-companion/`、`hardware/` | — | 暂无 | 不在范围内 |
| `windows/` | C#/.NET 8 | 暂无 | 不相关，另一个平台 |

## `CodeIslandCore` 的可移植性（实测统计）

我逐个文件统计了 import：

- **47 / 50 个文件只 import Foundation** —— 事件归一化、会话折叠、用量扫描、hook 配置写入器，都是平台无关的纯逻辑。
- **3 / 50 个 import Darwin** —— `SocketPath.swift`、`JSONLTailer.swift`、`AgentTaskParsing.swift`。换 `libc` 即可。

**这意味着上游真正的资产是一张表**：为了适配 30 多家 CLI，它把每家的拼写差异、每个边界情况（Hermes 的 `on_session_end` 其实是回合结束而不是会话结束、Grok 会重复导入 Claude/Cursor 的 hook 导致一个事件送三遍）都摸清并写成了注释。这张表已经转写进 `crates/codeisland-core/src/event.rs`。

## 逐项差异

| 方面 | 上游（macOS） | 本项目（Linux/KDE） | 原因 |
|---|---|---|---|
| 界面框架 | SwiftUI + AppKit | Qt6 + QML + LayerShellQt | 见 `docs/资源占用实测.md` 的选型理由 |
| 界面形态 | 物理刘海展开面板 | 顶部居中悬浮胶囊（layer-shell） | 屏上没有物理刘海，硬凹凹口不成立；悬浮胶囊是最接近的形态 |
| 界面 ↔ 后端 | 同一进程内 Swift 调用 | D-Bus 会话总线 | KDE 原生路径，`qdbus6` 可手敲调试，以后要包成 plasmoid 时能直接复用 |
| socket 服务端 | `NWListener`（Network.framework） | `std::net::UnixListener` | 标准库足够，不引异步运行时 |
| 磁盘工具 | `stat` + `Darwin` | `std::fs::metadata` + `FileTypeExt` | — |
| 进程追踪 | 走 `sysctl` 拿进程祖先链，用于生成 `session_id` 回退、区分 IDE 的子 agent 进程、折叠多并发卡片 | **未实现** | 缺 `session_id` 的事件目前选择丢弃而非编造。宁可少一张卡片，不要一张错的卡片 |
| 配置写入 | 直接改 `~/.claude/settings.json` 等全局文件 | **未实现**；冒烟测试用项目级 `.claude/settings.json` | 见下「一个已知坑」 |
| 更新机制 | Sparkle 2 + Homebrew cask | 未定 | 阶段 4 |
| 移动端 / 硬件 | Apple Watch、ESP32 | 未定 | 阶段 4 |
| 推送渠道 | Bark、ntfy、钉钉、飞书、企业微信、Slack、Telegram | 未定，倾向 ntfy | 阶段 4 |

## 一个已知坑：不要碰全局 `settings.json`

本机记忆库里有实测记录（`personal/facts/agent/记忆层/claude-code/claude-code-settings重写丢hooks.md`，2026-09-30）：**Claude Code 在配置变更时会重新生成 `~/.claude/settings.json`，不保留外部安装器注入的键**——曾经把 9 个生命周期 hook 和 `autoMemoryEnabled` 一次性全丢掉，而且不报错，表现为「采集静默停止」。

本机这个文件已经被 ponytail、cc-switch 等多家工具改过，且里面的 `permissions.defaultMode` 是 `bypassPermissions`。

所以：

1. **阶段 0 的冒烟测试绝不写全局配置**，只用一次性的项目级 `.claude/settings.json`。
2. 阶段 3 做 hook 自动安装时，必须实现**安装后复查**：写完读回来核对，发现被外部重写就重新装并提示用户。上游的 Hook Health Check 是同一个思路。
3. 不把 `bypassPermissions` 当成可以依赖的前提——它是用户当前的设置，不是这个项目的假设。

## 有意为之的偏离

| 偏离 | 说明 |
|---|---|
| 权限请求在阶段 0 无回复 | 没有界面可以问人。回 `deny` 会改变用户行为，回 `allow` 是伪造授权。沉默 = CLI 回落自己的提示 |
| 缺 `session_id` 的事件直接丢弃 | 上游会合成 `<source>-ppid-<pid>`。那需要进程祖先链，且合成出来的 id 一旦不准会让卡片串台。留到有真实需求的阶段 |
| 不引异步运行时 | 并发量是「一台机器上每个工具调用一个事件」，线程模型绰绰有余。省掉 tokio 及其依赖树 |
