# 协议

两条链路，一条用 unix socket，一条将来用 D-Bus。本文件是它们的事实来源；改动必须同步更新这里和对应的 `crates/codeisland-core/src/protocol.rs`。

## 链路一：hook → 桥接程序 → 常驻程序

### 桥接程序的调用方式

agent CLI 通过它自己的 hook 机制拉起桥接程序，载荷走 stdin：

```jsonc
// stdin，由 CLI 写入；字段随 CLI 不同而不同
{
  "hook_event_name": "PreToolUse",   // CLI 自己的拼写
  "session_id": "…",
  "tool_name": "Bash",
  "tool_input": { "command": "ls -la" },
  "cwd": "/home/…"
}
```

命令行可选参数：

| 参数 | 作用 |
|---|---|
| `--source <名字>` | 声明是哪个 CLI。用于区分同名事件不同来源，如 `claude` / `codex` / `pi` |
| `--event <名字>` | 给 stdin 里没有 `hook_event_name` 的 CLI 补充事件名 |

环境变量：

| 变量 | 作用 |
|---|---|
| `CODEISLAND_SOCKET_PATH` | 覆盖 socket 路径（测试、SSH 远程场景用） |
| `CODEISLAND_SKIP` | 只要被设置就立即静默退出，什么都不做 |
| `CODEISLAND_DEBUG` | 打开调试日志 |
| `CODEISLAND_BRIDGE_LOG` | 调试日志落盘位置，默认 `/tmp/codeisland-bridge.log` |

**调试日志绝不写 stdout**——stdout 是协议通道，混进任何东西都会破坏它。

### socket

| 项 | 值 |
|---|---|
| 路径 | `CODEISLAND_SOCKET_PATH`，否则 `/tmp/codeisland-<uid>.sock` |
| 类型 | `AF_UNIX` / `SOCK_STREAM` |
| 权限 | `0600`，只允许属主读写 |
| 方向 | 每个连接一个请求：桥接写一帧后保持连接打开，等常驻程序关闭连接作为回复结束 |
| 载荷上限 | 10 MiB（上游为容纳 Codex 的大文件 diff 而设的下限） |
| 分隔 | 请求是一行 JSON，以换行符结束（紧凑 JSON 不含裸换行，分隔符不会出现在载荷里） |
| 存活判定 | 桥接**不**半关闭写端。挂起等人批准的期间，常驻程序靠读端 EOF 判断 agent 是否已经退出；若桥接半关闭，每张卡片都会立刻被误判为"agent 已走" |

### 桥接程序发出的报文

一个 JSON 对象：

```jsonc
{
  "source": "claude",
  "event": "PreToolUse",           // CLI 原始拼写
  "normalized_event": "PreToolUse",// 归一化后的名字
  "session_id": "…",
  "cwd": "/home/…",
  "tool_name": "Bash",
  "tool_input": { "command": "ls -la" },
  "summary": "Bash: ls -la",       // 仅用于显示
  "ts_ms": 1791876277386,
  // CLI 原始载荷里其它字段原样保留
}
```

未建模的字段一律保留（`#[serde(flatten)]`），这样后续阶段能读到新字段而不用改桥接程序。

### 常驻程序回复

| 事件类别 | 回复 | 桥接程序行为 |
|---|---|---|
| 状态事件 | `{}` | 不做任何输出，正常退出 |
| 权限请求 | **空，不回复** | 不输出，退出码 0，CLI 回落自己的权限提示 |
| 问题 | **空，不回复** | 同上 |
| 常驻程序没跑 | — | 不输出，退出码 0 |
| 超时 | — | 不输出，退出码 0 |

**阶段 0 里权限请求永远无回复**，因为还没有界面可以问人。沉默是唯一诚实的答案：回 `deny` 会改变用户行为，回 `allow` 是伪造授权。

### 权限决策的报文格式

等阶段 2 有了界面，常驻程序回这个（逐字节对照上游源码与已安装的 `claude` 二进制里的字面量确认）：

```json
{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}
```

`behavior` 取 `allow` 或 `deny`。桥接程序把这个 JSON 原样写到 stdout，CLI 读它。

### 提问（AskUserQuestion）的契约（2026-10-14 交互式会话实测；初版写于 2026-10-13，只对照了二进制）

阶段 3 的"回答问题"按下面这几条做。**已核实的**与**尚未核实的**分开列——本节最初的写法把两个钩子面混为一谈，那一版断言已被实测替换。

已核实：

1. **提问不走 `Notification`**。上表里"问题不可回复"说的是 `Notification`——那条通道是只读的。
2. `allow` 决策可以带 `updatedInput`，且必须是对象（二进制字面量：*"an allow decision whose updatedInput is not an object"*）。
3. **`Other` 选项由 CLI 自动追加**，界面不要自己造（*"There should be no 'Other' option, that will be provided automatically"*）。
4. **提问确实以 `PermissionRequest` 到达**：`tool_name = "AskUserQuestion"`，`tool_input.questions` 是数组。事件顺序实测为 `PreToolUse` → `PermissionRequest` → `PostToolUse`。
5. 实测到的单个问题字段是 `header` / `question` / `multiSelect` / `options[{label, description}]`，样本（原样摘自 journal）：

   ```json
   {"questions":[{"header":"Color","question":"Red or blue?","multiSelect":false,
     "options":[{"label":"Red","description":"The red option."},
                {"label":"Blue","description":"The blue option."}]}]}
   ```

6. **回答 = `allow` + `updatedInput`**：原 `questions` 原样保留，外加 `answers`（key 是**问题原文**，value 是选项 `label`）和 `annotations`。工具随后就以这个 input 执行，`PostToolUse` 里能复核：

   ```json
   {"answers":{"Red or blue?":"Red"},"annotations":{},"questions":[… 原样 …]}
   ```

尚未核实（不能当成前提）：

7. `multiSelect: true` 时 `answers` 的值是**数组还是字符串**——实测样本只有单选，两种都没试过。
8. `text` / `number` 在真实载荷里长什么样：二进制字面量说存在三种 `type`（`choice`/`text`/`number`），但实测到的 `choice` 载荷里**根本没有 `type` 字段**。所以文本框/数字框的真实形状仍然未知。
9. `annotations` 的语义——实测样本里它是空对象 `{}`，推测是逐题补充说明（对应 `Other` 的自由文本），未见非空样本。

验证方法（可重放）：真 pty 里跑 `claude --model haiku`，让模型调用 `AskUserQuestion`，用一个临时 hook 命令返回 `updatedInput`，然后**提交指令之后一个键都不再按**。若 `PostToolUse` 出现 `answers: {"<模型自己写的问题原文>": "Blue"}`，而 `"Blue"` 只有那个 hook 会选，答案就只能来自 hook。2026-10-14 以此坐实，夹具在 `~/ci-ask-fixture/`（`answer-hook.py` + `drive6.py`）。另注意 **`-p` 非交互模式下该工具被禁用**（2026-10-13 实测），所以这条路径只有交互式会话能触发，测试必须在 pty 里跑。

结论：第 6 条已坐实，提问卡可以动工。但第 7–9 条落实之前，**卡片只回答已知的形状**：认不出的问题（无 `options`、`multiSelect` 语义未定、text/number）一律**静默**——不 park、不改写 `tool_input`，让 CLI 自己收答案。半套 choice 实现加上对未知问题乱改写，比不做更糟。

### 事件日志的保真度（2026-10-14 修正）

桥接程序过去把**未建模字段整段丢掉**（`extra` 直接给空表），所以事件日志里看到的并不是 CLI 真正发来的东西。现在它把未建模字段原样带上，只有两条护栏：

- `tool_response` **永不携带**——PostToolUse 的工具输出可以是几 MB，而日志是用户磁盘上只追加的文件
- 单个值超过 512 字节就截断，字符串尾部加省略号；对象/数组不猜结构，替换成 `{"truncated_bytes": N}`

这条改动的直接后果：`Stop` 事件里的 `message`（agent 这一轮最后说了什么）现在能到常驻程序，"完成了一轮"的通知因此有内容可写。在此之前那条通知只能显示兜底文案。**教训**：文档里"日志保留未知字段"这句话，在桥接这一段其实一直不成立，写保证之前应该先看一眼真实字节。

### codex 的 hook 契约（2026-10-14 实测，codex-cli 0.162.1）

注册文件是 `~/.codex/hooks.json`，结构与 Claude Code 的 `hooks` 段**同构**：

```json
{"hooks": {"PermissionRequest": [{"hooks": [{"type": "command",
  "command": "/path/codeisland-bridge --source codex", "timeout": 120}]}]}}
```

事件集也对得上：`SessionStart` / `UserPromptSubmit` / `PreToolUse` / `PermissionRequest` / `PostToolUse` / `Stop`。审批载荷同样带 `tool_name` 与 `tool_input.command`，**桥接与常驻程序未做任何改动就走通了**：真交互式 codex 触发 `PermissionRequest` → 脚本化 viewer 回答 `allow` → 被批准的文件确实被写出（三条件同时成立才算 PASS）。codex 还会在输出里自己打印 `hook: Stop Completed`，可作旁证。

四条实测边界，写代码时别踩：

1. **只在交互式问**。`codex exec`（非交互）从不发 `PermissionRequest` —— 与 claude `-p` 禁用 `AskUserQuestion` 是同一类陷阱：模式会关掉你要观测的那条路径
2. **问不问还取决于沙箱**。默认 `workspace-write` 允许写 `/tmp`，所以"写 /tmp"根本不触发审批；把沙箱收成 `-c sandbox_mode="read-only"` 并写项目内路径才稳定地问出来。据此造"必问"的场景，别假设它会问
2b. **codex 认项目级 `.codex/hooks.json`（2026-10-14 实测）**。把 `$CODEX_HOME/hooks.json` 删掉、只在项目里放一份，提示即报"5 hooks are new or changed"，带绕过旗标跑一次真指令，五个事件全部到达 daemon。所以 `codeisland-hookctl --source codex` 默认只写项目级，与本仓库"不碰全局 CLI 配置"的纪律一致。

   **codex 其实有两道门，第二道比 hook 信任更早咬人**：第一次进入某个目录，它会先问是否信任该文件夹；那一句没答完，会话根本不建立，hook 一个事件都不会发。同一份配置实测：已信任目录 5 个事件、新目录 0 个事件。排查时务必分清楚是"没建会话"还是"没批 hook"，否则又会像今天这样把环境假象读成协议结论。

3. **hook 有信任门槛，但信任是持久的**。首次运行会弹：

   ```text
   Hooks need review
   6 hooks are new or changed. Hooks can run outside the sandbox after you trust them.
   › 1. Review hooks   2. Trust all and continue   3. Continue without trusting (hooks won't run)
   ```

   选 2 之后 codex 把决定**写进 `config.toml`**，每条一行：

   ```toml
   [hooks.state."<hooks.json 路径>:<事件蛇形名>:0:0"]
   trusted_hash = "sha256:…"
   ```

   此后**不带任何旗标**再跑，提示不再出现、hook 照常执行 —— 实测裸 `codex` 收到 `SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / Stop` 五个事件。默认光标停在 `1. Review hooks`，所以自动化脚本必须按 **Down → Enter**，直接回车只会打开审阅列表。
   注意 `trusted_hash` 是按**命令内容**算的：改了 `command` 就等于改了哈希，提示会重新出现。所以 `codeisland-hookctl` 修复陈旧路径之后，必须告诉用户"再去 codex 里信任一次"，不能假设静默生效
4. **`args` 键不生效**。写成 `{"command": b, "args": ["--source","codex"]}` 时，桥接收到的 `source` 是 `unknown`；把参数并进 `command` 字符串才对
5. 顺带一条会咬人的：`approval_policy="untrusted"` 在此版本**已被移除**，带上它 codex 直接拒绝启动（`Error: ... is no longer supported; remove this setting`）

还有一条会咬人的测试陷阱：**codex 有一个共享的 app-server 守护进程**（`$CODEX_HOME/app-server-daemon/…/bin/codex`），新的 `codex` 调用只是附着到它。于是**每个用例改的 `CODEISLAND_SOCKET_PATH` 根本不生效** —— hook 沿用的是那个旧进程启动时的环境。我因此连着两次得出"信任不持久、仍需旗标"的错误结论，直到让 hook 自己把环境吐出来（看到 `socket_env=` 是上一轮的值）才发现。测 codex 之前先确认没有残留的夹具 app-server 进程；判据是 hook 自己转储的环境，不是"我明明设了变量"。

另外 codex 会**持久化批准结果**（`~/.codex/.codex-global-state.json` 里有 `approvals` / `approvalPolicy`），所以第二次跑同一件事就不会再问了 —— 重复实验要用干净的 `CODEX_HOME`，并且**别把带状态的 sqlite 与 global state 一起拷过去**（拷了就把要测的行为测没了）。

### 超时

| 场景 | 超时 | 依据 |
|---|---|---|
| 连接 | 250 ms | 本地 socket 要么立刻成功要么立刻失败 |
| 状态事件等回复 | 1 s | 事件已经送达，回复只是确认 |
| 权限/问题等人 | 3600 s | 够长，走开一会儿不会丢决策；够短，卡死的常驻程序最终会释放 agent |

### 事件名归一化

各家 CLI 对同一个生命周期时刻的叫法都不同。归一化后系统内部只认一套词：

| 归一化名 | 拼写来源 |
|---|---|
| `SessionStart` | `sessionStart`（Copilot）、`agentSpawn`（Kiro）、`session_start`（Trae）、`TaskStart`（Cline）、`on_session_start`（Hermes） |
| `UserPromptSubmit` | `beforeSubmitPrompt`（Cursor）、`userPromptSubmitted`（Copilot）、`pre_llm_call`（Hermes）、`TaskResume`（Cline） |
| `PreToolUse` | `beforeShellExecution` / `beforeReadFile` / `beforeMCPExecution`（Cursor）、`preToolUse`（Copilot）、`pre_tool_use`（Trae）、`pre_tool_call`（Hermes） |
| `PostToolUse` | `afterShellExecution` / `afterFileEdit` / `afterMCPExecution`（Cursor）、`AfterTool`（Gemini）、`postToolUse`（Copilot） |
| `PermissionRequest` | `BeforeTool`（Gemini）、`permission_request`（Trae） |
| `Notification` | `afterAgentThought`（Cursor）、`errorOccurred`（Copilot） |
| `Stop` | `stop`（Cursor）、`stop_failure` / `StopFailure`（Grok）、`on_session_end`（Hermes） |
| `SessionEnd` | `sessionEnd`（Copilot）、`session_end`（Trae）、`on_session_finalize` / `on_session_reset`（Hermes） |

完整表格和逐条注释在 `crates/codeisland-core/src/event.rs`，逐条转写自上游的 `Sources/CodeIslandCore/EventNormalizer.swift`。

### 路由规则

```
normalized == "PermissionRequest"                    → 权限（阻塞）
normalized == "Notification" 且载荷里有 question 字段 → 问题（阻塞）
其它                                                  → 状态事件（不阻塞）
```

上游专门留了一条规则文档警告：**这套判断在两个地方各写了一遍，曾经漂移过**，导致一边阻塞、另一边当成不阻塞处理。本项目的桥接程序和常驻程序都调同一个 `EventNormalizer::route_kind()`，从结构上消除这类漂移。

## 回复方向是 EOF 结束，不是换行结束（2026-10-14 由 pi 适配器暴露）

两个方向的收尾方式**不一样**，这一点文档以前没写清，结果第一个非 Rust 适配器就踩了：

- **请求方向（适配器 → daemon）**：一行 JSON 加 `\n`。daemon 用 `BufRead::read_until(b'\n')` 取帧，之后保持连接，用 EOF 判"agent 死了"。
- **回复方向（daemon → 适配器）**：一行 JSON，**不带尾随换行**。Rust 桥接程序用 `read_to_string` 读到 EOF，所以从来不需要换行；常驻程序那边就是 `stream.write_all(body.as_bytes())`。

踩坑实况：pi 的扩展适配器照搬"按换行切帧"的直觉去解析回复，于是 `deny` 永远解析不出来、走到"岛不在场"的兜底分支，headless `-p` 下就放行了。第一次看板上写成"驳回失败"，其实同时混着两个原因（另一个是测试 viewer 只答一个请求就退出，被驳回后模型重试的第二个请求无人应答）。

写进文档的判据：**适配器要按"能解析就解析、流结束再兜一次"处理回复**，不要要求尾随换行；测试驳回闭环时必须**持续应答每一个请求**，并检查 `PostToolUse` 是否出现 —— 2026-10-14 实测：allow 有 `PostToolUse`，deny 没有。这是"工具真的没跑"的硬证据，比模型自己说了什么可靠。


## 链路二：界面与常驻程序的关系

**修订（2026-10-13）**：原本计划界面作为独立进程通过 D-Bus 连常驻程序。实测
`spike/layer-shell-blur-test/README.md` 之后改成：**界面进程自己拥有 socket 服务端**，
`codeisland-daemon` 保留为无界面（headless）运行方式，两者共用
`codeisland-core`，同一时刻只有一个能 bind socket。

理由：界面必须是 C++/Qt 启动器（要申请 alpha 缓冲区），既然已经有 C++ 进程，
再拆一个常驻程序就是多一个常驻内存；单进程也更接近上游形态（上游的
`HookServer.swift` 就跑在 app 进程里）。代价是重启界面会让正在等待批准的 agent
拿到空回复——而这恰好是安全契约定义的回落行为，不是故障。

### 界面发回的三种命令（view socket，换行分帧 JSON）

| 命令 | 语义 | 对挂起 hook 的影响 |
|---|---|---|
| `permission_decision` | 人已决定：`behavior` allow/deny，提问卡另带 `answers` | 回包 allow/deny（提问卡回改写后的 input） |
| `jump` | 纯视图动作：把会话的终端带到前台 | **无**——hook 继续挂着，卡不撤 |
| `withdraw`（2026-10-15，F3） | 「这个问题我去终端里答」：撤卡，提问卡与审批卡均可用 | **沉默**——与 viewer 断连同路径，CLI 落回自己的提示 |
| `set_notify`（2026-10-15 晚，工具条铃铛） | 开/关「回合完成」桌面提醒 | **无**——只改告诉**人**什么，不改变告诉 agent 任何东西 |

`withdraw` 是安全契约的直接应用：跳过不是拒绝，也不批准任何东西，daemon 把挂起请求原样释放（`pending.withdraw` → 桥接收到 EOF → CLI 自己再问）。提问卡因此不再是死胡同——没有一个选项合适时，人总能点「跳过」。按钮常驻可用（不像「提交回答」要选满才亮）：它不代任何人承诺任何事。审批卡暂未放此按钮（拒绝/批准已覆盖两端，语义无缺口）。按钮的物理点击验证受本机环境限制（与「跳回终端」同一条遗留项，等 ydotool），但撤卡链路已用真实 viewer socket 全程实测：卡撤、会话降级、CLI 侧沉默三条件齐备。

## 链路三：发现（不靠 hook 也能看见会话）

**修订（2026-10-14）**：hook 是**证据**——agent 亲自说自己存在，还挂着一个 socket。但只在 hook 装好之后启动的 agent 才会说话，于是三个 CLI 都在跑而岛上空无一物。发现层补上这个盲区，同时不假装自己懂得一样多。

### 会话字段与 `origin`

视图帧里每个会话带的字段如下（`ViewUpdate` 定义在 `crates/codeisland-core/src/session.rs`）：

```jsonc
{
  "id": "2026-10-14T12-26-11-219Z_01a13a60-…",  // 就是存档文件名
  "source": "pi",
  "status": "working",        // working | idle | waiting_approval | waiting_input
  "cwd": "/home/…",
  "detail": "存档 · message",
  "origin": "discovered",     // hook | discovered（旧帧缺省为 hook）
  "tool_calls": 3,
  "last_event_ms": 1791983489860,
  "started_ms": 1791983000000
}
```

`origin` 不是装饰，它是**关于真实性的断言**：

| origin | 含义 | 允许的状态 |
|---|---|---|
| `hook` | agent 亲自上报，有 socket 为证 | 六种都可以，包括 `waiting_approval` / `waiting_input` |
| `discovered` | 从一个活进程拥有的存档文件配对而来 | `working` / `idle` / `done` / `error`——**读自存档记录的回合生命周期**；永远不说 awaiting 类状态 |

理由：存档能证明「这个 turn 开始没开始、完没完」，不能证明「它卡在等人回答」。等待批准是 socket 上的挂起请求，没有 socket 就没有可证明的东西。所以发现层永远不说 awaiting 类状态。

状态**不是**从 mtime 猜的（2026-10-14 改）。上游不猜——它读 harness 亲手写进 transcript 的回合记录，本岛照做：

| harness | 存档里记录了什么 | 读到什么就报什么 |
|---|---|---|
| codex | `event_msg` 的 `payload.type`：`task_started` / `task_complete` / `turn_aborted` / `turn_failed` | started 且后面没有终止 → `working`；complete → `done`；aborted/failed → `error` |
| pi | 最后一条 `message` 的 `role` 与内容块 | assistant 带 `toolCall` → `working`（在等工具结果）；`toolResult` / `user` → `working`；assistant 只有 text → `done` |
| claude | 最后一条 `assistant`/`user` 行 | 带 `tool_use` → `working`；`user` 行是 `tool_result` → `working`；assistant 纯 text → `done` |

实现：`crates/codeisland-core/src/turn.rs` 的 `turn_state()`，从尾部（64 KB 窗口）往新读，取**第一条**能认出回合含义的记录——最新记录描述现在，更早的 `task_complete` 不能压过后来的 `task_started`。认不出来（`None`）才退回 mtime 新鲜度，且那种行才带 `·推断` 标签——`status_stated` 字段把「文件说的」与「猜的」分开，界面不再一视同仁。

### 发现怎么配对（`crates/codeisland-daemon/src/discover.rs`）

一个进程单独说明不了它里面是哪个会话，一个存档单独说明不了人还在不在。**把两边的证据凑在一起**才等于「这个会话是活的」。证据分强弱，依次用：

1. **进程开着某个命名了会话的文件**——最硬。两种形态：直接开着 transcript（codex 的 app-server 为它服务的每个 thread 都开着 rollout）；或开着 codex 写的 `~/.codex/thread-writer-locks/<uuid>.lock`（它用**文件名**宣告这个 thread 活着）。同一个守护进程可以同时拥有多个会话，所以这个是**一对多**。
2. **进程坐在 transcript 所在目录里**（或是 agent 在那儿开的 shell，往上追 6 层父进程）。次硬，而且是一对一。只在 transcript 是该 harness 最新一份、或足够新时才认——因为便宜：本机每个 codex 进程都坐在 `$HOME`，而一条四小时前的旧会话 transcript 里记的也是 `$HOME`，光靠目录相等就会把**早已结束的会话报成在跑**（实测踩到）。
3. **新鲜度兜底**：某个 harness 有 N 个活进程，就认它最新的 N 份存档里、时间够近的那些。这是给 pi 兜底的：pi 把自己 chdir 到 `$HOME`，且**不持有** transcript（整棵进程树采样 12 次、零命中，而 codex 每次命中），所以前两条对它都不成立。

第 2、3 两档是弱证据，共用一条硬规则（2026-10-15）：**存档的最后写入不得早于该 harness 所有活进程的启动时刻**（留 10 秒容差，对齐上游 `claudeSession` 的 "must be modified after process started"，同样 10 秒）。一个进程启动之前写完的存档属于已经结束的上一个会话——实测：用户新开一个空的 pi（什么都没发，pi 的存档要等首条消息才落盘），岛却把 12 分钟前结束的旧会话复活挂在新进程头上。进程启动时间读 `/proc/<pid>/stat` 的 `starttime` 加 `/proc/uptime`（已对照 `ps -o lstart` 验证，误差 ≤1 秒）；读不到时规则整体不生效，退回旧行为。第 1 档（fd / 锁）不受此限：锁文件是 harness 自己写的「这个 thread 活着」声明，它比我们从时钟里算出来的任何东西都硬。

其它约束：

- **没有活进程的 harness 直接跳过**。没 hook、没进程的存档是历史，不是会话。
- **一个 id 只占一行**。codex 的同一个 thread 可能有两份 rollout（`<uuid>.jsonl` 与 `<uuid>_<uuid2>.jsonl`），两份都会配上同一个锁；按**最新**那份胜出，否则行里显示的是旧 transcript 的内容（实测：曾因此把正在干活的会话报成 idle，副行显示 `event_msg`）。
- **子代理折进它所属的会话**。codex 的 Guardian review 在 `session_meta.payload.parent_thread_id` 里指向被审阅的主对话；pi 把子代理跑批次嵌在父会话目录下（`<父会话>/<子uuid>/run-0/session.jsonl`）。子代理是会话里的一步，不是并列的第二个会话——**但只在父会话也在显示时才折**，否则孤儿子代理会默默消失。
  > 与上游的偏离：上游把它做成设置项（`pluginSessionMode`，默认 `separate`，只折已完成的子会话）。本岛只要父会话在就折，是**相反的默认值**，且是有意的：一个紧凑药丸把“审查者”与“被审查的对话”并列为两个，读起来就是“两个 agent 在跑”，而实际只有一个。
- **身份来自可执行文件，不是命令行**。曾用 argv 子串匹配，把提到名字的 shell 当成了 agent。现在的规则：`argv[0]` 是解释器（`node`/`bun`/`deno`）时 `argv[1]` 才算脚本；否则可执行文件名必须**正好**是 `claude` / `codex` / `pi`。
- **cwd 与 session_id 从存档头部读**，有上限（64 KB），按文件大小缓存。本机的 pi 存档实测 **12 MB**。
- **存活看存档 mtime**：在提示符前停了一小时是「安静」，不是「死了」。扫描周期 5 秒，某行连续 30 秒不再被配到就删除。mtime 只回答「还在不在」；「在干什么」由上面的回合记录回答，mtime 只在记录认不出时兜底。

### 行的标题（2026-10-15）

行的主标签是**对话自己的标题**，排版对齐上游 `SessionHeadline`：项目目录名加粗打头，`#标题` 灰字跟随；无标题时只剩项目名。三家各读各的（对齐上游 `SessionTitleStore.swift`，它只支持 codex/claude，pi 的首条提问是本岛自己的兑底）：

| harness | 标题来源 | 兑底 |
|---|---|---|
| codex | `~/.codex/session_index.jsonl` 的 `thread_name`（codex 自己写的线程名索引，追加有序，同一 id 末行胜） | 首条用户提问 |
| claude | transcript 里的 `custom-title`/`ai-title` 行（自定义优先；本机实测存在） | 首条用户提问 |
| pi | 无标题记录 | 首条用户提问 |

首条用户提问是三家共用的兑底：claude 的 `<local-command-caveat>`/`<command-name>` 等终端管道行不算对话，跳过。标题只在有值时写入（`None` 不清空已有标题）；写入不碰 `last_event_ms`——标题晚到不是活动，不该重排顺序、重置超时。缓存按文件大小失效：文件还在长就重读（首条提问、claude 中途写的标题都能补上），停了就定型。hook 行同样拿得到标题：hook 事件只带 cwd 不带标题，发现扫描读到 transcript 时顺带给两种 origin 的行都补上。

### 行的用量（底栏，2026-10-15 晚）

底栏的用量数字**只来自 harness 自己申报的计数器**，不估算：

| harness | 来源 | 状态 |
|---|---|---|
| codex | `event_msg`/`token_count` → `payload.info.total_token_usage`（harness 自己维护的会话累计，取末行即总量；本机两天的 rollout 里有 941 行） | ✅ 已接 |
| claude | `message.usage` 是**逐响应**计数，会话总量需全量求和（12 MB 存档不可接受） | ❌ 待有界的来源再做 |
| pi | 无结构化用量记录（实测只有正文里提到 "token"） | ❌ 无源 |

数字按工具聚合：`codex 输入 165M 输出 659.4K`（上游同形：输入X 输出Y）；没有申报的工具不出现——底栏永远不显示估计值。`set_usage` 与 `set_title` 同规则：两种 origin 都写、`None` 不清空、不碰 `last_event_ms`（计数不是活动）。缓存与 cwd/title 同法（按大小失效）。解析缓存已收敛为单一 `ParseCache`（cwd/title/usage 三键）。

### 行上的「当前步骤」

发现行的副行是**该会话最后一个工具调用**——「它在干什么」是这个行要回答的问题，而工具调用是存档里最字面的答案。取三家各自实测的形状：

| harness | 位置 | 字段 |
|---|---|---|
| codex | `response_item` → `payload.type == "function_call"` | `name` + `arguments`（**JSON 字符串**，要再解析一次）|
| pi | `message.content[]` → `type == "toolCall"` | `name` + `arguments` |
| claude | `message.content[]` → `type == "tool_use"` | `name` + `input` |

描述取 `command`/`cmd`/`file_path`/`path`/`pattern`/`query`/`url` 里第一个存在的键，截到一行。`exec_command · ssh main 'echo ready && …'` 或 `bash · cargo test --release`。

codex 的 `update_plan` 特殊：它不给命令，给的是清单里的**位置**，所以报成 `update_plan · 2/3 改判定`（数 `status == "in_progress"` 那一项）。

找不到工具调用时的兑底（2026-10-15 重写，替代旧版直接报记录类型名的行为——旧版把 codex 的计数行读成了「存档 · event_msg」，零信息量）：

1. 尾窗从 16 KB 扩到 **64 KB**——实测最后一个工具调用距末尾 9 行但超过 16 KB（大段推理/回复把它挤出了窗口）；
2. 噪声行（`event_msg`、`token_usage_record`）两趟都跳过——回合生命周期是状态胶囊的事，计数行什么也不说；
3. 兑底改为**最后一条消息正文**（codex `output_text`、pi/claude 文本块）——完成回合的回复本身比任何类型名都信息量大；
4. 全是噪声时返回「无」而不是编一行。

> **尚未移植**：把整张 `{step,status}` 清单渲染成卡片上的进度条（上游的 `AgentTaskParsing.swift`，25077 字节，覆盖 Claude `TaskCreate`/`TodoWrite`、codex `update_plan`、Gemini `write_todos`、OpenCode `todowrite`）。见 `功能差距与路线图.md` 的 F8。

### 发现**做不到**的事（硬边界）

- **推断不出「在等什么」**。没有 socket，就没有挂起的请求可以证明。发现层只会说 `working` / `idle` / `done` / `error`——而且前两者之间、done 与 idle 之间，靠的是存档**写了什么**，不是文件多久没动。
- **没有活进程就什么都看不见**。会话结束后、hook 也没装的话，这一行就不在岛上（这是有意的：回想一个已经结束的会话不是「看到所有活着的 agent」）。
- **一个 harness 的并发会话数 ≤ 它的活进程数**（fd / 锁绑定的除外，那可以一对多）。同一 harness 同时开多个会话而只有一个进程时，只认最新的那几个——且弱证据配对还要求存档写在活进程启动之后（见上文），进程启动前写完的存档是上一个会话的遗物，不会被新进程复活。
- **只认三家**（claude / codex / pi）。新增 harness 要在 `Harness` 里补一条，并确认它的存档里有 cwd。
- **不是自动展开的理由**。岛只在「需要你」时才弹开；纯运行的会话不弹，只在药丸上计数，悬停可看。

## 会话行的寿命（2026-10-15）

一行什么时候从岛上消失，按 origin 分两条规则，各有各的依据（实现在 `session.rs` 的 `forget_hook_stale` / `forget_discovered_not_in`，由 daemon 的发现扫描线程顺带执行，不需要独立的维护定时器）：

| origin | 消失时机 | 依据 |
|---|---|---|
| `hook` | 事件流静默超过 **10 分钟**（`CODEISLAND_HOOK_STALE_MS` 可覆盖），且发现层配不到它、也没有挂起的卡 | 对齐上游 `defaultStaleIdleMinutes = 10`（无进程监控的会话） |
| `discovered` | 连续 **30 秒**没被配到 | 一轮扫描跳过不算死（慢目录遍历），两轮不算才删 |

hook 行的删除有三重护栏，任何一条成立就保留：

1. **发现层仍配得到**（`alive` 列表里有它）——agent 进程还活着。Linux 版用这个代替上游的进程监控；一个跑了一小时的长工具调用不会被误删。
2. **有挂起的卡**（pending 里 park 着它的请求）——人正被提问，删行会孤儿化卡片。
3. **未超过超时窗口**——agent 几分钟不说话还在思考是常态。

`SessionEnd` 只覆盖优雅退出。被 kill 的 agent、没装该事件的 CLI、演示残留（实测：hold-card.py 挂过的卡留下的行在事件停止一小时后仍显示 `working`、计入会话数）都靠这条超时兜底。

## 事件日志

常驻程序把每个事件追加到 `~/.local/state/codeisland/events.jsonl`（`CODEISLAND_JOURNAL` 可覆盖），一行一个 JSON 对象。每次写入立即 flush——被杀掉也不能丢最后几条。这是阶段 0 唯一的观察窗口，之后也是重建会话和排查异常卡片的依据。

## pi 的适配（2026-10-14 实测）

pi **没有 hook 配置文件**，扩展是加载进 agent 进程的模块（`~/.pi/agent/extensions/` 自动扫描、`<project>/.pi/extensions/` 项目级、或 `pi install <path>` 注册的 package）。所以"事件走 hook 命令"这条路对 pi 不成立，适配器改用一个 `tool_call` 处理器向 daemon 发同一套帧。

- **审批语义相反**：pi 的 `tool_call` 处理器「不返回」即放行。安全契约要求岛不能成为静默决定者，所以适配器在**岛不可达 / 无人应答 / 回复不可解析**时退回 `ctx.ui.confirm`；只有 `ctx.hasUI` 为假（headless `-p`）才原样继续 —— 那正是"交回 CLI"在无界面下的含义。
- **两个超时分开算**：连接 3s（`CODEISLAND_PI_CONNECT_MS`）与应答 120s（`CODEISLAND_PI_APPROVAL_MS`）。合用一个会让"socket 文件残留但没人 accept"吃掉整个应答预算。这不是假想：本机另有 pi 扩展在 turn-start 钩子里 await 远程调用，实测把首字拖到 89 秒，因为 **pi 在钩子 resolve 前不发模型请求**。所以状态帧一律 fire-and-forget，绝不 await。
- **生效条件**：项目级 `.pi/extensions/` 受信任门控（首跑要 `--approve`）；扩展只在启动时加载，当前会话不生效。
- **驳回判据不看模型说了什么，看 `PostToolUse` 有没有出现**。实测 allow 有、deny 没有；且被驳回后模型会**重试**，于是同一会话出现 `p1`、`p2` 两个请求 —— viewer 只答第一个就会把成功读成失败。
- 跳转不需要额外适配：适配器自己走 `/proc` 祖链，journal 里同样带 `emulator=konsole` 与 pid，常驻程序按同一规则处理。
