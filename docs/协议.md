# 协议

两条链路，一条用 unix socket，一条将来用 D-Bus。本文件是它们的事实来源；改动必须同步更新这里和对应的 `crates/codeisland-core/src/protocol.rs`。

## 链路一：hook → 桥接程序 → 常驻程序

### 桥接程序的调用方式

agent CLI 通过它自己的 hook 机制拉起桥接程序，载荷走 stdin：

```jsonc
// stdin，由 CLI 写入；字段随 CLI 不同而不同
{
  "hook_event_name": "PreToolUse",   // CLI 自己的拼写
  "session_id": "…",
  "tool_name": "Bash",
  "tool_input": { "command": "ls -la" },
  "cwd": "/home/…"
}
```

命令行可选参数：

| 参数 | 作用 |
|---|---|
| `--source <名字>` | 声明是哪个 CLI。用于区分同名事件不同来源，如 `claude` / `codex` / `pi` |
| `--event <名字>` | 给 stdin 里没有 `hook_event_name` 的 CLI 补充事件名 |

环境变量：

| 变量 | 作用 |
|---|---|
| `CODEISLAND_SOCKET_PATH` | 覆盖 socket 路径（测试、SSH 远程场景用） |
| `CODEISLAND_SKIP` | 只要被设置就立即静默退出，什么都不做 |
| `CODEISLAND_DEBUG` | 打开调试日志 |
| `CODEISLAND_BRIDGE_LOG` | 调试日志落盘位置，默认 `/tmp/codeisland-bridge.log` |

**调试日志绝不写 stdout**——stdout 是协议通道，混进任何东西都会破坏它。

### socket

| 项 | 值 |
|---|---|
| 路径 | `CODEISLAND_SOCKET_PATH`，否则 `/tmp/codeisland-<uid>.sock` |
| 类型 | `AF_UNIX` / `SOCK_STREAM` |
| 权限 | `0600`，只允许属主读写 |
| 方向 | 每个连接一个请求：桥接写一帧后保持连接打开，等常驻程序关闭连接作为回复结束 |
| 载荷上限 | 10 MiB（上游为容纳 Codex 的大文件 diff 而设的下限） |
| 分隔 | 请求是一行 JSON，以换行符结束（紧凑 JSON 不含裸换行，分隔符不会出现在载荷里） |
| 存活判定 | 桥接**不**半关闭写端。挂起等人批准的期间，常驻程序靠读端 EOF 判断 agent 是否已经退出；若桥接半关闭，每张卡片都会立刻被误判为"agent 已走" |

### 桥接程序发出的报文

一个 JSON 对象：

```jsonc
{
  "source": "claude",
  "event": "PreToolUse",           // CLI 原始拼写
  "normalized_event": "PreToolUse",// 归一化后的名字
  "session_id": "…",
  "cwd": "/home/…",
  "tool_name": "Bash",
  "tool_input": { "command": "ls -la" },
  "summary": "Bash: ls -la",       // 仅用于显示
  "ts_ms": 1791876277386,
  // CLI 原始载荷里其它字段原样保留
}
```

未建模的字段一律保留（`#[serde(flatten)]`），这样后续阶段能读到新字段而不用改桥接程序。

### 常驻程序回复

| 事件类别 | 回复 | 桥接程序行为 |
|---|---|---|
| 状态事件 | `{}` | 不做任何输出，正常退出 |
| 权限请求 | **空，不回复** | 不输出，退出码 0，CLI 回落自己的权限提示 |
| 问题 | **空，不回复** | 同上 |
| 常驻程序没跑 | — | 不输出，退出码 0 |
| 超时 | — | 不输出，退出码 0 |

**阶段 0 里权限请求永远无回复**，因为还没有界面可以问人。沉默是唯一诚实的答案：回 `deny` 会改变用户行为，回 `allow` 是伪造授权。

### 权限决策的报文格式

等阶段 2 有了界面，常驻程序回这个（逐字节对照上游源码与已安装的 `claude` 二进制里的字面量确认）：

```json
{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}
```

`behavior` 取 `allow` 或 `deny`。桥接程序把这个 JSON 原样写到 stdout，CLI 读它。

### 提问（AskUserQuestion）的契约（2026-10-14 交互式会话实测；初版写于 2026-10-13，只对照了二进制）

阶段 3 的"回答问题"按下面这几条做。**已核实的**与**尚未核实的**分开列——本节最初的写法把两个钩子面混为一谈，那一版断言已被实测替换。

已核实：

1. **提问不走 `Notification`**。上表里"问题不可回复"说的是 `Notification`——那条通道是只读的。
2. `allow` 决策可以带 `updatedInput`，且必须是对象（二进制字面量：*"an allow decision whose updatedInput is not an object"*）。
3. **`Other` 选项由 CLI 自动追加**，界面不要自己造（*"There should be no 'Other' option, that will be provided automatically"*）。
4. **提问确实以 `PermissionRequest` 到达**：`tool_name = "AskUserQuestion"`，`tool_input.questions` 是数组。事件顺序实测为 `PreToolUse` → `PermissionRequest` → `PostToolUse`。
5. 实测到的单个问题字段是 `header` / `question` / `multiSelect` / `options[{label, description}]`，样本（原样摘自 journal）：

   ```json
   {"questions":[{"header":"Color","question":"Red or blue?","multiSelect":false,
     "options":[{"label":"Red","description":"The red option."},
                {"label":"Blue","description":"The blue option."}]}]}
   ```

6. **回答 = `allow` + `updatedInput`**：原 `questions` 原样保留，外加 `answers`（key 是**问题原文**，value 是选项 `label`）和 `annotations`。工具随后就以这个 input 执行，`PostToolUse` 里能复核：

   ```json
   {"answers":{"Red or blue?":"Red"},"annotations":{},"questions":[… 原样 …]}
   ```

尚未核实（不能当成前提）：

7. `multiSelect: true` 时 `answers` 的值是**数组还是字符串**——实测样本只有单选，两种都没试过。
8. `text` / `number` 在真实载荷里长什么样：二进制字面量说存在三种 `type`（`choice`/`text`/`number`），但实测到的 `choice` 载荷里**根本没有 `type` 字段**。所以文本框/数字框的真实形状仍然未知。
9. `annotations` 的语义——实测样本里它是空对象 `{}`，推测是逐题补充说明（对应 `Other` 的自由文本），未见非空样本。

验证方法（可重放）：真 pty 里跑 `claude --model haiku`，让模型调用 `AskUserQuestion`，用一个临时 hook 命令返回 `updatedInput`，然后**提交指令之后一个键都不再按**。若 `PostToolUse` 出现 `answers: {"<模型自己写的问题原文>": "Blue"}`，而 `"Blue"` 只有那个 hook 会选，答案就只能来自 hook。2026-10-14 以此坐实，夹具在 `~/ci-ask-fixture/`（`answer-hook.py` + `drive6.py`）。另注意 **`-p` 非交互模式下该工具被禁用**（2026-10-13 实测），所以这条路径只有交互式会话能触发，测试必须在 pty 里跑。

结论：第 6 条已坐实，提问卡可以动工。但第 7–9 条落实之前，**卡片只回答已知的形状**：认不出的问题（无 `options`、`multiSelect` 语义未定、text/number）一律**静默**——不 park、不改写 `tool_input`，让 CLI 自己收答案。半套 choice 实现加上对未知问题乱改写，比不做更糟。

### 事件日志的保真度（2026-10-14 修正）

桥接程序过去把**未建模字段整段丢掉**（`extra` 直接给空表），所以事件日志里看到的并不是 CLI 真正发来的东西。现在它把未建模字段原样带上，只有两条护栏：

- `tool_response` **永不携带**——PostToolUse 的工具输出可以是几 MB，而日志是用户磁盘上只追加的文件
- 单个值超过 512 字节就截断，字符串尾部加省略号；对象/数组不猜结构，替换成 `{"truncated_bytes": N}`

这条改动的直接后果：`Stop` 事件里的 `message`（agent 这一轮最后说了什么）现在能到常驻程序，"完成了一轮"的通知因此有内容可写。在此之前那条通知只能显示兜底文案。**教训**：文档里"日志保留未知字段"这句话，在桥接这一段其实一直不成立，写保证之前应该先看一眼真实字节。

### codex 的 hook 契约（2026-10-14 实测，codex-cli 0.162.1）

注册文件是 `~/.codex/hooks.json`，结构与 Claude Code 的 `hooks` 段**同构**：

```json
{"hooks": {"PermissionRequest": [{"hooks": [{"type": "command",
  "command": "/path/codeisland-bridge --source codex", "timeout": 120}]}]}}
```

事件集也对得上：`SessionStart` / `UserPromptSubmit` / `PreToolUse` / `PermissionRequest` / `PostToolUse` / `Stop`。审批载荷同样带 `tool_name` 与 `tool_input.command`，**桥接与常驻程序未做任何改动就走通了**：真交互式 codex 触发 `PermissionRequest` → 脚本化 viewer 回答 `allow` → 被批准的文件确实被写出（三条件同时成立才算 PASS）。codex 还会在输出里自己打印 `hook: Stop Completed`，可作旁证。

四条实测边界，写代码时别踩：

1. **只在交互式问**。`codex exec`（非交互）从不发 `PermissionRequest` —— 与 claude `-p` 禁用 `AskUserQuestion` 是同一类陷阱：模式会关掉你要观测的那条路径
2. **问不问还取决于沙箱**。默认 `workspace-write` 允许写 `/tmp`，所以"写 /tmp"根本不触发审批；把沙箱收成 `-c sandbox_mode="read-only"` 并写项目内路径才稳定地问出来。据此造"必问"的场景，别假设它会问
2b. **codex 认项目级 `.codex/hooks.json`（2026-10-14 实测）**。把 `$CODEX_HOME/hooks.json` 删掉、只在项目里放一份，提示即报"5 hooks are new or changed"，带绕过旗标跑一次真指令，五个事件全部到达 daemon。所以 `codeisland-hookctl --source codex` 默认只写项目级，与本仓库"不碰全局 CLI 配置"的纪律一致。

   **codex 其实有两道门，第二道比 hook 信任更早咬人**：第一次进入某个目录，它会先问是否信任该文件夹；那一句没答完，会话根本不建立，hook 一个事件都不会发。同一份配置实测：已信任目录 5 个事件、新目录 0 个事件。排查时务必分清楚是"没建会话"还是"没批 hook"，否则又会像今天这样把环境假象读成协议结论。

3. **hook 有信任门槛，但信任是持久的**。首次运行会弹：

   ```text
   Hooks need review
   6 hooks are new or changed. Hooks can run outside the sandbox after you trust them.
   › 1. Review hooks   2. Trust all and continue   3. Continue without trusting (hooks won't run)
   ```

   选 2 之后 codex 把决定**写进 `config.toml`**，每条一行：

   ```toml
   [hooks.state."<hooks.json 路径>:<事件蛇形名>:0:0"]
   trusted_hash = "sha256:…"
   ```

   此后**不带任何旗标**再跑，提示不再出现、hook 照常执行 —— 实测裸 `codex` 收到 `SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / Stop` 五个事件。默认光标停在 `1. Review hooks`，所以自动化脚本必须按 **Down → Enter**，直接回车只会打开审阅列表。
   注意 `trusted_hash` 是按**命令内容**算的：改了 `command` 就等于改了哈希，提示会重新出现。所以 `codeisland-hookctl` 修复陈旧路径之后，必须告诉用户"再去 codex 里信任一次"，不能假设静默生效
4. **`args` 键不生效**。写成 `{"command": b, "args": ["--source","codex"]}` 时，桥接收到的 `source` 是 `unknown`；把参数并进 `command` 字符串才对
5. 顺带一条会咬人的：`approval_policy="untrusted"` 在此版本**已被移除**，带上它 codex 直接拒绝启动（`Error: ... is no longer supported; remove this setting`）

还有一条会咬人的测试陷阱：**codex 有一个共享的 app-server 守护进程**（`$CODEX_HOME/app-server-daemon/…/bin/codex`），新的 `codex` 调用只是附着到它。于是**每个用例改的 `CODEISLAND_SOCKET_PATH` 根本不生效** —— hook 沿用的是那个旧进程启动时的环境。我因此连着两次得出"信任不持久、仍需旗标"的错误结论，直到让 hook 自己把环境吐出来（看到 `socket_env=` 是上一轮的值）才发现。测 codex 之前先确认没有残留的夹具 app-server 进程；判据是 hook 自己转储的环境，不是"我明明设了变量"。

另外 codex 会**持久化批准结果**（`~/.codex/.codex-global-state.json` 里有 `approvals` / `approvalPolicy`），所以第二次跑同一件事就不会再问了 —— 重复实验要用干净的 `CODEX_HOME`，并且**别把带状态的 sqlite 与 global state 一起拷过去**（拷了就把要测的行为测没了）。

### 超时

| 场景 | 超时 | 依据 |
|---|---|---|
| 连接 | 250 ms | 本地 socket 要么立刻成功要么立刻失败 |
| 状态事件等回复 | 1 s | 事件已经送达，回复只是确认 |
| 权限/问题等人 | 3600 s | 够长，走开一会儿不会丢决策；够短，卡死的常驻程序最终会释放 agent |

### 事件名归一化

各家 CLI 对同一个生命周期时刻的叫法都不同。归一化后系统内部只认一套词：

| 归一化名 | 拼写来源 |
|---|---|
| `SessionStart` | `sessionStart`（Copilot）、`agentSpawn`（Kiro）、`session_start`（Trae）、`TaskStart`（Cline）、`on_session_start`（Hermes） |
| `UserPromptSubmit` | `beforeSubmitPrompt`（Cursor）、`userPromptSubmitted`（Copilot）、`pre_llm_call`（Hermes）、`TaskResume`（Cline） |
| `PreToolUse` | `beforeShellExecution` / `beforeReadFile` / `beforeMCPExecution`（Cursor）、`preToolUse`（Copilot）、`pre_tool_use`（Trae）、`pre_tool_call`（Hermes） |
| `PostToolUse` | `afterShellExecution` / `afterFileEdit` / `afterMCPExecution`（Cursor）、`AfterTool`（Gemini）、`postToolUse`（Copilot） |
| `PermissionRequest` | `BeforeTool`（Gemini）、`permission_request`（Trae） |
| `Notification` | `afterAgentThought`（Cursor）、`errorOccurred`（Copilot） |
| `Stop` | `stop`（Cursor）、`stop_failure` / `StopFailure`（Grok）、`on_session_end`（Hermes） |
| `SessionEnd` | `sessionEnd`（Copilot）、`session_end`（Trae）、`on_session_finalize` / `on_session_reset`（Hermes） |

完整表格和逐条注释在 `crates/codeisland-core/src/event.rs`，逐条转写自上游的 `Sources/CodeIslandCore/EventNormalizer.swift`。

### 路由规则

```
normalized == "PermissionRequest"                    → 权限（阻塞）
normalized == "Notification" 且载荷里有 question 字段 → 问题（阻塞）
其它                                                  → 状态事件（不阻塞）
```

上游专门留了一条规则文档警告：**这套判断在两个地方各写了一遍，曾经漂移过**，导致一边阻塞、另一边当成不阻塞处理。本项目的桥接程序和常驻程序都调同一个 `EventNormalizer::route_kind()`，从结构上消除这类漂移。

## 链路二：界面与常驻程序的关系

**修订（2026-10-13）**：原本计划界面作为独立进程通过 D-Bus 连常驻程序。实测
`spike/layer-shell-blur-test/README.md` 之后改成：**界面进程自己拥有 socket 服务端**，
`codeisland-daemon` 保留为无界面（headless）运行方式，两者共用
`codeisland-core`，同一时刻只有一个能 bind socket。

理由：界面必须是 C++/Qt 启动器（要申请 alpha 缓冲区），既然已经有 C++ 进程，
再拆一个常驻程序就是多一个常驻内存；单进程也更接近上游形态（上游的
`HookServer.swift` 就跑在 app 进程里）。代价是重启界面会让正在等待批准的 agent
拿到空回复——而这恰好是安全契约定义的回落行为，不是故障。

## 事件日志

常驻程序把每个事件追加到 `~/.local/state/codeisland/events.jsonl`（`CODEISLAND_JOURNAL` 可覆盖），一行一个 JSON 对象。每次写入立即 flush——被杀掉也不能丢最后几条。这是阶段 0 唯一的观察窗口，之后也是重建会话和排查异常卡片的依据。
